# GophKeeper

Клиент-серверный менеджер паролей. Сервер хранит и синхронизирует зашифрованные приватные данные, CLI-клиент даёт к ним доступ с Windows, Linux и macOS.

Типы хранимых данных: пары логин/пароль, произвольный текст, бинарные данные, банковские карты. К любой записи прилагается произвольная текстовая метаинформация.

## Быстрый старт

Нужны Go 1.25+, Docker и `protoc` (только если меняете proto-контракт).

```bash
make build                           # бинарники в bin/
docker compose up -d postgres        # postgres на порту 5433
make cert                            # самоподписанный сертификат для локального TLS
```

Запуск сервера:

```bash
DATABASE_DSN="postgres://gophkeeper:gophkeeper@localhost:5433/gophkeeper?sslmode=disable" \
JWT_SECRET=dev-secret \
./bin/server -tls-cert dev-cert.pem -tls-key dev-key.pem
```

Работа клиентом (в другом терминале):

```bash
export GOPHKEEPER_CA_FILE=dev-cert.pem
./bin/client register --login alice
./bin/client add login-password --name github --login alice@example.com --metadata "work"
./bin/client list
./bin/client get github --reveal
```

Клиент спросит пароли интерактивно, без эха. Миграции применяются при старте сервера сами.

## Сборка

```bash
make build       # сервер и клиент для текущей платформы, в bin/
make build-all   # клиент для Linux, macOS (amd64 и arm64) и Windows
make test        # все тесты
make lint        # golangci-lint
```

Версия и дата сборки вшиваются через `-ldflags` и доступны обеим программам:

```bash
./bin/client version
```

## Команды клиента

| Команда | Что делает |
|---|---|
| `register --login <login>` | Создаёт аккаунт: спросит пароль аккаунта и мастер-пароль |
| `login --login <login>` | Вход на сервер |
| `logout` | Забывает токен, сессию и локальную копию |
| `list` | Показывает все записи (мастер-пароль не нужен) |
| `get <id\|name> [--reveal]` | Показывает запись; секретные поля скрыты без `--reveal` |
| `add login-password` | Добавляет пару логин/пароль |
| `add text` | Добавляет текстовую заметку |
| `add binary --file <path>` | Добавляет файл (до 4 МБ) |
| `add card` | Добавляет данные банковской карты |
| `delete <id\|name>` | Удаляет запись |
| `version` | Версия и дата сборки |

Запись адресуется по UUID или по имени. Если имя неоднозначно, клиент попросит указать UUID.

## Настройки

Приоритет: **флаги > переменные окружения > значения по умолчанию**.

Сервер:

| Флаг | Переменная | По умолчанию | Назначение |
|---|---|---|---|
| `-a` | `ADDRESS` | `localhost:3200` | адрес прослушивания |
| `-d` | `DATABASE_DSN` | — (обязательно) | строка подключения к Postgres |
| — | `JWT_SECRET` | — (обязательно) | ключ подписи токенов |
| `-l` | `LOG_LEVEL` | `info` | уровень логирования |
| `-token-ttl` | `TOKEN_TTL` | `24h` | время жизни одного токена |
| `-tls-cert` | `TLS_CERT_FILE` | — | сертификат; включает TLS вместе с ключом |
| `-tls-key` | `TLS_KEY_FILE` | — | приватный ключ |

У `JWT_SECRET` нет флага сознательно: аргументы командной строки видны другим процессам и остаются в истории шелла.

Клиент (только переменные окружения):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GOPHKEEPER_ADDRESS` | `localhost:3200` | адрес сервера |
| `GOPHKEEPER_CA_FILE` | — | сертификат сервера, если он самоподписанный |
| `GOPHKEEPER_INSECURE` | — | `1` отключает TLS (только для локальной отладки) |
| `GOPHKEEPER_HOME` | `~/.gophkeeper` | каталог состояния |
| `GOPHKEEPER_PASSWORD` | — | пароль аккаунта для скриптов |
| `GOPHKEEPER_MASTER_PASSWORD` | — | мастер-пароль для скриптов |

## Тесты

```bash
make test                                  # юнит-тесты, тесты БД скипаются
DATABASE_DSN="postgres://gophkeeper:gophkeeper@localhost:5433/gophkeeper?sslmode=disable" make test
```

Покрытие устроено по уровням: юнит-тесты пакетов, тесты хранилища против настоящего Postgres, функциональные тесты CLI (настоящий сервер поверх TLS с хранилищем в памяти) и интеграционные тесты в `internal/integration` — клиент, сервер и Postgres одновременно. Тесты, которым нужна база, пропускаются без `DATABASE_DSN`.

## Архитектура
- **Протокол:** gRPC поверх TLS. Контракт описан в [api/proto/gophkeeper/v1/gophkeeper.proto](api/proto/gophkeeper/v1/gophkeeper.proto), включая семантику ошибок каждого RPC.
- **Сервер** отвечает за аутентификацию, хранение и выдачу записей. Данные для него непрозрачны.
- **Клиент** делает всю криптографию: сервер никогда не видит открытых данных.

## Модель безопасности

### Два пароля

У пользователя два независимых секрета:

| Пароль | Зачем | Что видит сервер |
|---|---|---|
| Пароль аккаунта | Вход на сервер, получение JWT | Передаётся по TLS, хранится как Argon2id-хеш |
| Мастер-пароль | Шифрование данных | Никогда не покидает клиент |

### Схема DEK + KEK

1. При регистрации клиент генерирует случайный **DEK** (data encryption key, 32 байта). Все записи шифруются DEK'ом (AES-256-GCM).
2. Из мастер-пароля выводится **KEK** (key encryption key): `KEK = Argon2id(мастер-пароль, соль)`. Параметры Argon2id (стартово: memory 64 MiB, time 1, threads 4) и соль хранятся на сервере per-user — их можно усиливать со временем, не ломая старые аккаунты.
3. DEK хранится на сервере **обёрнутым** KEK'ом (AES-256-GCM) и выдаётся клиенту при логине.
4. Проверка мастер-пароля — успешная расшифровка DEK: при неверном пароле не сходится аутентификационный тег GCM, клиент получает понятную ошибку.

Смена мастер-пароля архитектурой поддерживается (перешифровать один DEK, а не все данные), в CLI первой версии реализована не будет.

### Что знает и чего не знает сервер

Сервер знает: логин, хеш пароля аккаунта, а также имена, метаинформацию, типы и времена изменений записей — имя и метаинформация хранятся открыто, чтобы сервер мог отдавать список и выполнять поиск без расшифровки. Сервер **не** знает: мастер-пароль, KEK, DEK и содержимое payload — сами логины/пароли, тексты, файлы и данные карт.

### Сессии и токены

- Вход по паролю аккаунта → JWT.
- Скользящее продление: каждый успешный ответ сервера несёт свежий токен в метаданных, клиент перезаписывает его.
- Токен хранится в `~/.gophkeeper/token` с правами 0600. Украденный токен позволяет лишь скачать шифроблобы — прочитать их без мастер-пароля нельзя.
- Мастер-пароль запрашивается интерактивно при каждой команде с данными и нигде не сохраняется. Для скриптов и тестов — переменная окружения `GOPHKEEPER_MASTER_PASSWORD`.

### Локальный кеш

Клиент хранит в `~/.gophkeeper/` (права 0600) кеш записей в том же виде, в каком они лежат на сервере: открытые имя/метаинформация + зашифрованный payload, плюс обёрнутый DEK с солью и параметрами KDF. Кеш обновляется полным снимком при каждой успешной синхронизации. Payload без мастер-пароля не читается, поэтому модель безопасности не меняется: секретная часть данных на диске защищена тем же шифрованием, что и на сервере.

## Модель синхронизации

- Несколько клиентов одного пользователя работают с одним сервером; источник истины — сервер.
- Каждый клиент держит локальный зашифрованный кеш и заменяет его полным снимком записей при каждой успешной синхронизации. Полный снимок заодно решает доставку удалений: стёртые записи просто исчезают из снимка.
- **Оффлайн-режим — чтение:** при недоступном сервере `get`/`list` работают из кеша. Создание, изменение и удаление требуют соединения — так конфликты разрешаются только на сервере.
- **Разрешение конфликтов — last write wins:** сервер принимает каждую запись и инкрементирует `version`; побеждает последний пришедший запрос. Поле `version` — информационное («запись изменилась»), сервер никогда не отклоняет запись из-за устаревшей версии. Это осознанный трейд-офф: для CLI-сценария одновременное редактирование одной записи — редкость, а детерминированное поведение проще объяснить и протестировать.
- **Удаление — мягкое** (tombstone): запись помечается `deleted` и исчезает из выдачи.

## Принятые решения

1. **gRPC, а не REST.** Строгий контракт через protobuf, кодогенерация клиента и сервера, бинарный протокол. Swagger при этом не используется — контрактом служит сам proto-файл с комментариями.
2. **E2E-шифрование на клиенте, а не серверное.** Для менеджера паролей компрометация сервера не должна раскрывать данные. Цена — невосстановимость данных при утере мастер-пароля (см. Ограничения).
3. **DEK+KEK, а не ключ напрямую из пароля.** Позволяет менять мастер-пароль без перешифрования всех данных и даёт дешёвую проверку корректности пароля.
4. **Argon2id везде.** И для хеша пароля аккаунта на сервере, и для KDF мастер-пароля на клиенте: один криптостек.
5. **Last write wins, а не оптимистическая блокировка.** Меньше кода и состояний.
6. **PostgreSQL.** Реляционная схема тривиальна (две таблицы).
7. **JWT со скользящим продлением.** Не нужны refresh-токены и их хранение/отзыв; активная сессия не протухает.
8. **Имя и метаинформация записи — открытые.** Сервер может отдавать список и искать по ним без расшифровки (решение по итогам ревью). Цена — названия записей видны серверу; секретное содержимое (payload) остаётся зашифрованным всегда.

## Ограничения

- **Лимит записи — 4 MB** (стандартный лимит gRPC-сообщения).
- **Утеря мастер-пароля = утеря данных.** Восстановление невозможно by design: сервер не располагает ничем, что помогло бы расшифровать DEK.
- **Оффлайн — только чтение:** без сервера доступны `get`/`list` из локального кеша (по состоянию на последнюю синхронизацию). Запись оффлайн не поддерживается.
- Одновременное редактирование одной записи с разных клиентов разрешается по last write wins — «проигравшая» версия не сохраняется.
- **Изменения записи в CLI нет:** правка делается удалением и добавлением заново. Серверный API `UpdateSecret` при этом реализован и покрыт тестами.
- Самоподписанный сертификат из `make cert` — для локальной работы. Для реального сервера нужен сертификат от удостоверяющего центра, тогда клиенту не нужен `GOPHKEEPER_CA_FILE`.

## Схема БД

Две таблицы — [migrations/000001_init.up.sql](migrations/000001_init.up.sql):

- `users`: логин, Argon2id-хеш пароля аккаунта + крипто-материал клиента (`kek_salt`, `kdf_params`, `encrypted_dek`).
- `secrets`: тип записи, открытые `name` и `metadata`, зашифрованный блоб payload, `version`, флаг `deleted`.

## Структура репозитория

```
api/proto/            — proto-контракт (источник истины API)
pkg/proto/            — сгенерированный gRPC-код
cmd/server/           — entrypoint сервера
cmd/client/           — entrypoint CLI-клиента
cmd/certgen/          — генератор сертификата для локального TLS
internal/server/      — auth, secrets, хранилище, gRPC-слой, конфиг
internal/client/      — crypt (KDF, AES-GCM), payload, store, remote, cli
internal/secret/      — доменный тип записи, общий для клиента и сервера
internal/tlscert/     — генерация и настройка TLS
internal/integration/ — интеграционные тесты (клиент + сервер + Postgres)
migrations/           — SQL-миграции (golang-migrate, embed)
```
